Executive Summary
This report provides a rigorous engineering deep-dive into the  Arbitration &
Divergence Logic, a critical safety component within the trading system. The
primary function of this module, termed the Data Arbiter, is to act as a real-
time validation gate for trading signals generated by the  ThetaData source. It
performs this check by comparing the signal's price against a near-simultaneous
price from a reference source, Interactive Brokers (IBKR).
The core specification is a validation check:  abs(Theta_Price - IBKR_Price) <
Threshold. If the price divergence exceeds a pre-defined threshold, the trading
signal is rejected to prevent execution based on potentially erroneous or stale
data.  This  analysis  deconstructs  the  mechanism,  proposes  a  robust
implementation  strategy  addressing  the  critical  challenge  of  timestamp
alignment,  and  performs  a  critical  analysis  of  potential  failure  modes,  edge
cases, and optimizations.

1.0 Technical Deconstruction
The  Data Arbiter is  fundamentally  a  cross-source  data  consistency  check,
acting  as  a  final  sanity  check  before  capital  is  committed  to  a  trade.  Its
architecture and logic can be broken down into the following core components:
Primary Data Source (Signal):ThetaData. This is the source that
generates the actionable trading signal, containing information such as the
asset, direction (buy/sell), and the price at which the signal was generated
(Theta_Price at T_theta).
Reference Data Source (Ground Truth):IBKR. This is treated as the
system's source of truth for real-time market prices. For this check, we are
interested in the IBKR_Price at T_ibkr.
Triggering Event: The arrival of a new trading signal from ThetaData.
Core Validation Logic: A mathematical comparison to ensure the two data
sources are in agreement within an acceptable margin of error. 
plaintext // Formula Is_Divergent = abs(Theta_Price - IBKR_Price) >=
Threshold
Threshold: A configurable parameter (e.g., 0.1% or 0.001) that defines the
maximum allowable percentage difference between the two prices. This
value represents the system's tolerance for minor, expected discrepancies
between data feeds.
Action: A binary decision:
ACCEPT: If Is_Divergent is false, the signal is considered valid and
is passed to the execution engine.
REJECT: If Is_Divergent is true, the signal is discarded, and the
event is logged for analysis. This prevents trading on a signal that
does not align with the reference market price.
The central engineering challenge is not the mathematical comparison itself, but
ensuring the comparison is temporally relevant. Market prices are highly time-
sensitive, and comparing a price from time T with one from T - 5 seconds is
meaningless. Therefore, handling the temporal misalignment between T_theta
and T_ibkr is the most critical aspect of this component's design.

2.0 Implementation Strategy
This section outlines a practical approach to building the  Data Arbiter class,
focusing  on  its  architecture,  handling  of  asynchronicity,  and  the  logic  for
temporal alignment.
2.1 Class Design and Data Flow
A DataArbiter class should encapsulate the validation logic. It requires access
to a real-time stream of IBKR market data. The system should not "request" the
IBKR price upon receiving a Theta signal, as that would introduce significant
network latency. Instead, it should maintain a subscription to the relevant IBKR
market data feed and use the most recently received quote.
Data Flow: 1. A ThetaData signal object is received by the trading logic. 2. The
signal  is  passed  to  the  DataArbiter.validate_signal() method.  3.  The
validate_signal method immediately accesses the  latest availableIBKRQuote
from its internal state (which is continuously updated by a separate subscription
thread/process). 4. The arbiter performs the timestamp and price comparison. 5.
It  returns  a  validation  result  (e.g.,  ACCEPT,  REJECT_DIVERGENCE, 
REJECT_STALE_REFERENCE_DATA). 6. The parent trading logic acts on the result.

# --- Data Arbiter Class ---
classDataArbiter:
"""
    Validates trading signals against a reference market data source (IBKR).
    """
def__init__(self,divergence_threshold:float=0.001,latency_window_ms:
int=500):
"""
        Initializes the arbiter.
        Args:
            divergence_threshold (float): Max allowed percentage difference 
(e.g., 0.001 for 0.1%).
            latency_window_ms (int): Max time difference in milliseconds between 
signal and quote.
        """
self.divergence_threshold=divergence_threshold
self.latency_window=timedelta(milliseconds=latency_window_ms)
# This would be populated by a separate thread listening to the IBKR 
feed.
# The key is the symbol string.
self._latest_ibkr_quotes:dict[str,IBKRQuote]={}
defupdate_ibkr_quote(self,quote:IBKRQuote):
"""
        Callback method to be invoked by the IBKR data handler.
        This should be called every time a new quote arrives from IBKR.
        """
self._latest_ibkr_quotes[quote.symbol]=quote

defvalidate_signal(self,signal:ThetaSignal)->tuple[ValidationResult,
str]:
"""
        Performs the arbitration and divergence check.
        """
symbol=signal.symbol
# 1. Check for presence of reference data
latest_quote=self._latest_ibkr_quotes.get(symbol)
ifnotlatest_quote:
return(ValidationResult.REJECT_NO_REFERENCE_DATA,
f"No reference IBKR quote available for {symbol}")
# 2. Handle Timestamp Alignment & Staleness
# The IBKR quote must be recent relative to the signal's timestamp.
time_diff=abs(signal.timestamp-latest_quote.timestamp)
iftime_diff>self.latency_window:
return(ValidationResult.REJECT_STALE_REFERENCE_DATA,
f"IBKR quote is stale. Time diff: 
{time_diff.total_seconds()*1000:.0f}ms "
f"(Window: {self.latency_window.total_seconds()*1000:.0f}
ms)")
# 3. Perform Divergence Check
price_diff=abs(signal.price-latest_quote.price)
threshold_value=signal.price*self.divergence_threshold
ifprice_diff>=threshold_value:
percentage_diff=(price_diff/signal.price)*100
return(ValidationResult.REJECT_DIVERGENCE,
f"Price divergence exceeded. Theta: {signal.price}, IBKR: 
{latest_quote.price}. "
f"Diff: {percentage_diff:.4f}% > Threshold: 
{self.divergence_threshold*100:.4f}%")
# 4. Signal is valid
return(ValidationResult.ACCEPT,
f"Signal accepted. Theta: {signal.price}, IBKR: 
{latest_quote.price}")

2.3 Defining the Acceptable Latency Window
The  latency_window is  a  critical  parameter  that  defines  how  close  in  time
T_theta and T_ibkr must be. A window that is too narrow will cause excessive
rejections  due  to  normal  network  jitter;  a  window  that  is  too  wide  risks
comparing prices from different market states.
Methodology for Determining the Window:
Baseline Measurement: Measure the end-to-end latency of both the
ThetaData and IBKR data feeds under normal operating conditions. The
window should be at least as large as the typical, observed delta between
the arrival times of correlated messages.
Start Conservatively: Begin with a reasonable but tight window, for
example, 250-500 milliseconds. This is a common range in low-to-
medium frequency systems.
Empirical Tuning: Log all rejections due to staleness. Analyze the
distribution of time_diff for these rejections. If a large number of
rejections occur with a time difference just outside the window (e.g., 510ms
when the window is 500ms), it suggests the window may be too tight for
current network conditions.
Volatility Consideration: In highly volatile markets, the price can change
significantly within milliseconds. A tighter window is safer. Consider
making the window dynamically adjustable based on a real-time volatility
index (e.g., VIX) or the asset's Average True Range (ATR).
A starting value of  500ms is a robust, conservative choice, subject to tuning
based on empirical performance data.

3.1 Potential Failure Modes
Stale Reference (IBKR) Feed:
Problem: The IBKR data feed disconnects or lags significantly. The 
DataArbiter would be comparing fresh ThetaData signals against an
old, irrelevant IBKR_Price.
Mitigation: The implemented latency_window check is the primary
defense. It correctly identifies the IBKR data as stale relative to the
signal. A secondary, independent health check should monitor the
IBKR feed itself. If no new quote has been received for any symbol for 
N seconds (e.g., N=5), the system should enter a "safe mode" and
reject all trades, flagging the IBKR feed as down.
System Clock Skew:
Problem: The server running the arbiter has a clock that is out of
sync with the ThetaData or IBKR servers. This will invalidate all
timestamp comparisons.
Mitigation: All machines involved in the trading pipeline must be
synchronized to a reliable time source using NTP (Network Time
Protocol). While minor sub-millisecond drift is unavoidable, NTP
synchronization prevents catastrophic clock-related errors.
Flash Crashes / Extreme Volatility:
Problem: During a market flash crash, prices can move several
percent in under a second. The DataArbiter will correctly reject
signals as divergent, effectively halting trading.
Analysis: This is a feature, not a bug. The arbiter's purpose is to
prevent trading under uncertain or anomalous conditions. A rapid
divergence between two data feeds is a textbook definition of such a
condition. The system should halt and alert a human operator.

3.2 Edge Cases
Illiquid Assets & Wide Spreads:
Problem: For illiquid assets, the bid-ask spread can be wider than the
divergence threshold. The definition of "price" (e.g., last trade, mid-
price, bid, ask) becomes critical. Comparing Theta_Price (which
might be a mid-price) to IBKR's last_trade_price could lead to
constant false rejections.
Mitigation: Ensure the price types being compared are identical
(e.g., mid-price vs. mid-price). The divergence_threshold may need to
be configured on a per-asset basis, with higher thresholds for less
liquid instruments.
System Startup (Warm-up Phase):
Problem: When the system starts, the _latest_ibkr_quotes cache is
empty. The first few ThetaData signals will be rejected with 
REJECT_NO_REFERENCE_DATA.
Mitigation: The system should have a defined "warm-up" state. It
should not process any ThetaData signals until it has received at least
one valid quote for each subscribed symbol from IBKR, ensuring the
arbiter is primed with reference data.
3.3 Optimizations
Dynamic Thresholding:
Concept: A fixed 0.1% threshold may be too restrictive for a volatile
asset but too loose for a stable one. The threshold should be dynamic.
Implementation: Set the threshold as a multiple of a short-term
volatility measure, such as the 1-minute Average True Range (ATR). 
math Threshold_Value = Price * (Base_Threshold_Percent +
Multiplier * ATR_1min) This allows the arbiter to adapt to changing
market regimes automatically.

Enhanced Logging and Metrics:
Concept: To effectively tune the arbiter, detailed data is required.
Implementation: For every validation, log the Theta_Price, 
IBKR_Price, their respective timestamps, the calculated time delta,
the price difference (absolute and percentage), and the final decision.
Expose these metrics to a monitoring system (e.g., Prometheus/
Grafana) to visualize rejection rates, average divergence, and latency
deltas over time. This data is invaluable for post-mortem analysis and
parameter tuning.
